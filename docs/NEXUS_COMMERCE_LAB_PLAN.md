# NEXUS Commerce Lab — Delivery Plan & Source Integrity

Updated: 2026-10-16 · Owner: E-Commerce analytics portfolio project

## Goal

Ship a professional, **owned** and freely deployable storefront testing surface so the team can measure genuine browser interactions (with consent), real Lighthouse lab performance and its own Google Analytics 4 property. Keep its sandbox purchase flow, historical TheLook analytics and unrelated demo websites isolated. Production claims must be grounded in a specific source system and reporting period.

```text
    |

    |-- events, order_items, products, users -> dbt -> Power BI

```

## Labeling and exclusions

- Illustrative catalog prices are **UI examples**, not business revenue or BigQuery TheLook values.
- The mock checkout **cannot accept real payment** and stores no user address, card number, email, or user identity. It sends no network request to any commerce backend.
- Any GA4 activity must be generated by genuine visitors browsing this site and explicitly consenting, not by replaying or inventing 2.4 million historical events.
- Source-specific custom events: `lab_page_view`, `lab_view_item`, `lab_add_to_cart`, `lab_remove_from_cart`, `lab_checkout_completed`. These are operational test events and may be used for source-qualified lab conversion counts only.
- No GA4 `purchase`, `refund`, `begin_checkout`, `value`, `currency`, `transaction_id` or `user_id` is emitted; thus revenue, CAC and ROAS remain unavailable.
- Analytics script only loads **after visitor opt-in** when a valid GA4 Measurement ID is configured. A denial still permits checkout.
- Each public/sandbox chart must include source, collection date, and a clearly readable `LAB / TEST CHECKOUT` status. No hidden fake business traffic.
- Track the performance and accessibility of the controlled site separately from third-party demo benchmark pages.
- The lab's static assets are open; the GitHub repository is not an authenticated commerce service.

## Release acceptance checklist

- Run `node --test storefront/tests/*.test.mjs`.
- Run `node storefront/scripts/build.mjs`. Must build with analytics disabled by default.
- Run `NEXUS_GA4_MEASUREMENT_ID=G-ABCDEF1234 node storefront/scripts/build.mjs` and ensure only a valid Measurement ID enters the public config, not a service-account key.
- Serve the dist directory locally and test keyboard navigation, cart limits, checkout, consent opt-in/deny and refresh.
- Deploy to an owned Vercel project with **Root Directory = storefront**. No authorized deployment is claimed by source commits.
- Open the deployed site and verify PageSpeed Mobile/Desktop. A known third-party demo storefront cannot substitute for this evidence.
- Verify GA4 DebugView after consenting on actual hosted domain; confirm no purchase/revenue events.
- Only then publish a case-study update, with explicit separate TheLook and lab source identities.

## Risks

- Real GA4 events will not exist until a valid property and public deployment are configured.
- Google consent/legal notice will need review for the selected jurisdiction and intended audience before public production release.
- Local page preview is not a representative Lighthouse benchmark for a global CDN.
- Vercel quotas, project access and custom domains must be verified against connected infrastructure.
- The static site creates no server-side commerce database and thus cannot be described as a production e-commerce platform.
